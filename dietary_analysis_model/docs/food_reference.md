# 식품 영양성분 참조 데이터 분석 — 푸드렌즈 기반 식이분석에 쓸 수 있는가 (2026-10-21)

대상: `00_Data/전국통합식품영양성분정보_전체_20260929.csv`
(식약처 전국통합식품영양성분정보 표준데이터, Open API `tn_pubr_public_nutri_info_api` 전체 346,592행, 데이터 기준일 2026-09-29).
도구: `tools/download_nutri_std.py`(다운로드), `tools/build_food_reference.py`(가공), `data/food_code_classification.csv`(코드 → 분류).

**전제 (2026-10-21 확인):** 현재 `meal_food`의 영양성분은 참조 데이터가 1인분 기준이 아니어서 쓸 수 없었기 때문에
LLM이 음식명을 보고 1인분 기준으로 추정해 작성한 값이다. 참조 데이터 표준화와 1인분 환산이 끝나면 `meal_food`는
**참조의 1인분 환산값**으로 적재되고, 사용자가 입력한 인분 수(`serving_qty`, 예: 1.5)를 곱해 섭취량이 반영된다.
따라서 이 문서의 참조 데이터 작업은 분석 보조가 아니라 `meal_food` 적재의 원천을 만드는 일이다.

> **현재 상태 (2026-10-26).** 1인분 환산(§7)과 매핑표 1차(§8)는 완료. 매핑표의 목적지는 loop-dev `sibc.meal_food_master`(식약처 기준 식품 21,172건, 100 g/100 ml 기준)이며, 2차는 이 마스터 체계로 만든다.
> 매핑 규칙 2건(우선순위·검수 기준 유지 여부, 원재료 1인분 선보강 여부)은 보류 상태다. 앱 음식명은 `meal_food.food_name_norm` 누적으로 확보한다.

질문 네 가지에 답한다.
1. 푸드렌즈 기반 식이분석의 기초 데이터로 쓸 수 있는가
2. 우리가 수집·저장하는 데이터가 모두 들어 있는가
3. 음식 섭취량에 따라 영양분석이 가능한 수준으로 가공할 수 있는가
4. 가공한 참조를 쓰는 것과 원본을 그대로 쓰는 것 중 무엇이 나은가

### 3.2 현재 `meal_food` 값(LLM 추정)과의 차이

dev 데이터의 음식명 100건을 참조와 이름으로 맞춰 보면, LLM이 추정한 1인분 kcal와 참조 1인분 kcal가 ±30% 이내인 경우는 33%뿐이다
(현미밥: LLM 1공기 232 kcal vs 국건영 370 ml 448 kcal). 이는 참조의 오류가 아니라 **두 값의 "1인분" 정의가 다르기 때문**이며,
참조 기반 적재로 전환하면 사라지는 차이다. 전환 전후 데이터를 구분하려면 `meal_food`에 값의 출처(LLM 추정 / 참조 코드)를 남겨야 한다.

이름만으로 자동 매칭하면 엉뚱한 코드가 붙는다는 점은 별개의 문제다. 아메리카노 7건 중 1건은 200 kcal/100 g(분말), 나머지는 2~4 kcal/100 ml(음료).
쌀밥은 10 kg·20 kg 업소용 포장이 섞여 있다. 같은 이름에 코드가 2개 이상인 식품명이 27,567개(80,355행)다. 그래서 매핑표가 필요하다.

### 3.3 가공해서 가능한 수준으로 만들 수 있는가 — 가능하다. 단, 네 가지 규칙이 필요하다

| 규칙 | 내용 |
|---|---|
| **A. 코드 선택** | 음식명 → 코드는 자동 매칭이 아니라 **매핑표(검수)**로 고정. 후보 우선순위: 음식·산출 > 음식·분석 > 원재료 > 가공식품. 포장 중량 5~1,000 g 밖(업소용·대용량)은 제외. 기준 단위(g/ml)가 음식 성격과 맞는 것만 |
| **B. 1인분 환산** | 모든 영양값을 **1인분 값**으로 환산해 두고(7장), 섭취량은 **1인분 값 × 인분 수(`serving_qty`)**로 계산한다. 산출 음식(100 ml 기준)은 식품중량(ml)이 1인분이라 단위 환산이 필요 없고, 기준 g ↔ 1회량 ml가 다른 가공식품은 밀도 1.0을 가정한다 |
| **C. 1인분 출처 기록** | 1인분이 어디서 왔는지(`serving_source`: 식품중량 / 분할 / 식약처 1회 섭취참고량 / 포장 / 표준값)를 행마다 남겨, 앱이 사용자에게 "1인분 = 300 ml"처럼 보여주고 인분 수를 입력받을 수 있게 한다 |
| **D. 공란 유지·이상치 제외** | 공란은 NULL, 0은 0. 정합 ±25% 밖·극단값 행은 `quality_flag`로 표시하고 기본 선택에서 제외 |

이 규칙을 적용하면 `meal_food`에는 "참조 1인분 값"이 적재되고, ① 테이블의 영양 합계 = Σ(1인분 값 × 인분 수)로 지금 로직 그대로 계산된다. 미량영양소는 FULL 등급 음식에 한해 채워진다.

## 4. 원본을 그대로 쓸 것인가, 가공한 참조를 쓸 것인가

| 방식 | 장점 | 단점 |
|---|---|---|
| **원본 그대로** (음식명으로 조회, 100 기준값 × 섭취량) | 가공 없음, 최신 데이터 바로 반영 | 이름 하나에 코드 수십 개(소금빵 88개), 업소용 대용량 포함, g/ml 혼재, 공란·0 혼재 → 적재 시 어느 코드를 쓸지 정할 수 없음. 판정 근거를 "어느 코드"로 명시할 수 없음 |
| **가공 참조** (코드 고정 매핑표 + 단위 통일 + 등급·품질 플래그) | 음식마다 코드 1개가 고정되어 재현 가능, 미량영양소 등급 선택, 단위 오류 차단, 근거 추적성 | 매핑표 유지 작업(신규 음식명 주 1회 보강), 분기별 데이터 갱신 절차 필요 |

**판단: 가공 참조를 쓴다.** 원본은 "조회해서 바로 쓰는 표"가 아니라 "코드가 정해진 뒤 값을 꺼내는 사전"이다. 가공은 값을 바꾸는 것이 아니라 (1) 음식명 → 코드 고정, (2) 단위·분량 해석, (3) 품질 플래그 세 가지뿐이므로 원본 값의 무결성은 유지된다. 원본 CSV는 변경 없이 보관하고, 가공 참조는 원본에서 재생성한다(`build_food_reference.py`).

실행 형태: 전체 346,591행을 DB나 git에 올릴 필요는 없다. 매핑표에 등장하는 코드의 행만 추린 **소형 참조(수천 행)**를 git에 두고 갱신 작업이 읽는다. 전체 CSV는 로컬 보관 + 분기 재다운로드.

## 5. 결론 (질문별)

1. **기초 데이터로 사용 가능.** 국내 공식 데이터이고 KDRIs 판정에 필요한 영양소·단위가 맞다. 다만 자동 조회용이 아니라 **매핑표와 함께** 써야 한다.
2. **수집 영양소 21개 중 20개 포함.** 비타민 E 없음. 니아신은 NE 환산 불가. 미량영양소는 음식·산출 3,140건(상용 음식)에서만 완전하다 — 푸드렌즈 음식의 상당수(밥·국·찌개·볶음·구이)가 여기에 해당한다.
3. **섭취량 기반 분석이 가능한 수준으로 가공 가능.** 모든 값을 1인분으로 환산해 두고(7장) 인분 수를 곱한다. 코드는 매핑표로 고정한다.
4. **가공 참조가 낫다.** 원본은 보관하고, 코드 고정·단위 해석·품질 플래그만 더한 참조를 재생성해서 쓴다.

## 8. 매핑표 1차 (2026-10-21)

도구 `tools/build_food_code_map.py`, 산출 `data/food_code_map.csv` (dev 음식명 102종, `data/food_names_dev.txt`).

### 8.1 매칭·선택 규칙

1. 이름 정규화(공백·기호 제거, 소문자) 후 **정확 일치 → 앞부분 일치**(참조 `음식명_재료`의 앞부분) **→ 접두 일치**(우리 이름으로 시작하는 참조명, 한글만) 순으로 후보를 찾는다. 없으면 `UNMAPPED`.
2. 1인분이 없거나 품질 플래그(2인분 의심, 범위 밖, 에너지 정합 위반, 극단값)가 있거나 포장 1,000 g/ml 초과(업소용)인 후보는 제외.
3. 우선순위: 등급 FULL > PARTIAL > CORE → 유형 음식 > 원재료 > 가공식품 → 생성방법 산출 > 분석 > 수집 → 플래그 적은 것 → 1인분이 100 미만인 음식 후순위 → 짧은 이름.
4. 1순위를 매핑하되, 정확 일치가 아니거나 후보 간 1인분 kcal 차이가 1.3배를 넘거나 플래그가 있으면 `reviewed = N`(검수 필요), 그 외 `AUTO`. 검수자가 `Y`로 바꾼 행은 재생성 시 유지.

### 8.2 1차 결과 (102종)

| 구분 | 건수 |
|---|---|
| 정확 일치 | 55 |
| 앞부분·접두 일치 | 15 |
| 미매칭 | 32 (영문·오타·임의 입력: whopper, string, 진짜너무칼로리높은거 …) |

### 8.3 결과가 보여주는 것

- **검수 필요의 대부분은 "같은 이름, 다른 1인분"이다.** 김치찌개 28개 코드 중 산출 FULL 행이 200 ml 38 kcal, 짬뽕 637 ml 465 kcal, 현미밥 370 ml 448 kcal처럼 국건영 1인분 변종이 여러 개라 kcal가 2~7배 벌어진다. 자동 선택만으로는 어느 변종이 "앱의 1인분"에 맞는지 정할 수 없으므로 사람이 한 번 고정해야 한다.
- **원재료에 1인분이 없어 과일·우유가 가공식품으로 간다.** 바나나 → 가공 바나나 30 g. 원재료 1인분(KDRIs 1인 1회 분량: 과일 100 g, 우유 200 ml 등)을 붙이면 해결된다 (7.4 항목 3).
- **접두 일치는 여전히 위험하다.** 견과류 → "견과류 두유…". 한 글자·일반명(빵, 전, 밥)은 자동 매핑하지 않고 앱이 더 구체적인 이름을 주도록 하는 편이 낫다.
- 실제 음식명 목록은 dev와 성격이 다를 것이므로(테스트 입력 다수), `meal_food.food_name_norm`이 충분히 누적된 뒤에 매핑률을 말할 수 있다.
