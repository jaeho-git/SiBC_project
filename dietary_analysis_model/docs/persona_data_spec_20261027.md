# 페르소나 데이터 명세 — 시스템 구축·논리 검증용 합성 사용자 (2026-10-27)

설계 문서 [system_design_20261022.md](system_design_20261022.md) §8의 4~7단계(행동 층, 습관 층, 웨어러블 결합, 맥락 층)를
실제 데이터가 충분히 쌓이기 전에 끝까지 구현하고 검증하기 위한 합성 데이터의 명세다. 생성기는 이 문서를 그대로 코드로 옮기며,
문서의 수치마다 출처를 적어 "그럴싸한 가정"이 아니라 "측정된 분포"에서 뽑히게 한다.

생성기 버전: `persona.2026.10.27-v1` (2026-10-27 구현, 보정 통과). 보정 목표 수치의 조회 시점은 **2026-10-27, release DB 집계, 식이 기록 창 2026-09-01~10-26**이다.

---

## 0. 목적과 경계

### 0.1 왜 만드는가

loop-dev의 식이 기록(17명, 104끼니)으로는 7/14/30/60/180일 창, 재계산, 조건표 6종, 창 상태 3종을 한 번도 끝까지 밟을 수 없다.
release DB에는 기록이 있지만 운영 데이터이므로 읽기만 하고, 개인 행을 복사하지 않는다는 규칙이 있다. 그래서 **우리가 쓰는 테이블 포맷에 맞춰**,
**실제 사용자 분포에 보정된** 합성 사용자를 만들어 그 위에서 시스템을 구축한다.

### 0.2 할 수 있는 것

| 용도 | 설명 |
|---|---|
| 규칙 논리의 정확성 | 하루 분류 4종, 창 상태 3종, 결론 조건표 6종, 방향 결정 순서 8행, 재계산 35일, 경계값 처리를 모든 분기에서 시험한다. 실제 데이터에서 거의 안 나오는 "비교 불가", "체중 추세 반전", "긴급"을 의도적으로 만든다 |
| 구현과 계약 검증 | 테이블 ①②③ 확장, 행동 층·습관 층 갱신 코드, 출력 레코드(설계 §4)의 열 정의와 앱 파트 시연 |
| 복원력 평가 | 페르소나는 **진짜 섭취·소모·체중을 우리가 아는** 데이터다. 과소보고 탐지가 과소보고 페르소나를 잡는지, 섭취만 경로가 완전 경로와 같은 방향을 내는지, 결측 민감도(설계 §5.1)를 정답 대비로 측정한다 |
| 평가 절차의 예행 | 안정화 곡선, 학습 곡선, 재계산 변동률을 **절차로서** 미리 돌려 본다. 수치는 실제 데이터로 다시 낸다 |

### 0.3 할 수 없는 것

- 임계값 확정(추세 ±5%, 균형 폭 ±150 kcal, 과소보고 하한 1.35, 최소 유효 일수). 페르소나는 우리가 넣은 가정으로 만들어지므로 그 가정을 다시 확인하는 것은 순환이다.
- 거짓 알람률 측정, 국민건강영양조사 백분위의 타당성, 행동 변화 효과. 실제 사용자에서만 나온다.
- README 원칙 "합성 데이터나 smoke 결과를 실제 성능으로 보고하지 않는다"는 그대로 적용된다. 페르소나로 나온 모든 수치는 문서·그림에서 **"합성"**으로 표기한다.

### 0.4 격리 규칙

1. 합성 데이터는 **로컬 파일로만** 만든다(2026-10-27 결정). 공유 자원인 loop-dev와 release DB에는 어떤 형태로도 적재하지 않는다. 생성기는 DB 접속 코드를 갖지 않는다.
2. 실제 사용자와 섞이지 않게 사용자 식별자는 UUID 첫 블록을 `99999999`로 고정하고, 로컬 PostgreSQL에 올릴 때도 별도 스키마 `sibc_persona`를 쓴다(§1.4).
3. 운영 데이터는 **집계값만** 쓴다(§6의 보정 목표표). 개인 행은 읽지도, 복사하지도 않는다. 합성 사용자는 어떤 실제 사용자와도 1:1 대응하지 않는다.
4. 생성기는 코드 + 시드 + 버전 있는 매개변수 파일로 두고 언제든 같은 결과를 다시 만든다. 매개변수마다 출처 열을 둔다.
5. 생성 산출물(CSV·SQL)은 `01_Results/persona/`(git 제외)에 두고, 저장소에는 생성기·매개변수·유형표·음식 풀·검증 결과 요약만 둔다. 생성기 구현과 데이터 생성은 별개 행동이며, 생성은 지시가 있을 때 실행한다.

- 생성기는 `01_Results/persona/`에 CSV 6종과 `load_local.sql`, `run_info.json`을 쓴다. 공유 DB에는 적재하지 않는다.

## 2. 생성 구조 — 진실 층과 관측 층

### 2.1 두 층을 나누는 이유

설계 원칙은 "미기록과 결식, 미착용과 비활동을 구분한다"다. 이것을 시험하려면 **실제로 먹었는데 기록하지 않은 날**과 **실제로 안 먹은 날**이
데이터에 따로 존재해야 한다. 그래서 먹은 사실(진실)과 기록된 사실(관측)을 두 단계로 만든다.

```text
프로필 (성·연령·키·체중·BMI·활동 수준·장치·가이드라인)
  → 진실 층: 날마다 진짜 섭취(끼니별 열량·영양소), 진짜 소모, 진짜 체중, 결식 여부, 운동 세션
      → 관측 층: 기록 여부(A축) · 기록 왜곡(C축) · 음식 분해 · 착용/부분 착용(D축) · 체중계 측정(D축) · 수신 지연
          → 출력 테이블: user_master, meal, meal_food, baseline_lifelog_daily
          → 정답표: persona_manifest, persona_truth_daily
```

### 2.2 `persona_manifest` 열

| 열 | 내용 |
|---|---|
| `user_id`, `persona_code`, `instance_no` | 식별 |
| `axis_a_recording`, `axis_b_value`, `axis_c_observation`, `axis_d_device` | §4·§5의 축 코드 |
| `sex`, `age`, `height_cm`, `weight_kg_start`, `bmi_start`, `pal`, `bmr_kcal` | 프로필과 기초대사량(Mifflin-St Jeor) |
| `true_intake_factor`, `trend_slope_pct_per_week`, `weekend_factor`, `snack_share`, `late_night_rate` | 값 패턴의 진실 매개변수 |
| `underreport_factor`, `snack_drop_rate` | 관측 왜곡 매개변수 |
| `wear_rate`, `partial_rate`, `device_bias`, `scale_freq_per_month`, `arrival_delay_profile` | 장치 매개변수 |
| `guideline_code` | 의료진 지정 가이드라인(없으면 NULL) |
| `start_date`, `end_date`, `gap_start`, `gap_end` | 기록 기간과 공백 |
| `seed` | 재생성용 |

### 2.3 하루 생성 절차

1. **진짜 하루 섭취 열량** = 기대 섭취량(§3.1) × `true_intake_factor` × 추세 계수(주차별) × 주말 계수 × exp(N(0, σ_day)). σ_day는 개인 내 변동 계수 0.25에 해당(§6).
2. **결식 결정**: 아침 결식률 등 끼니별 결식 확률(§3.2)로 실제 결식을 정한다. 결식한 끼니의 열량은 다른 끼니에 60%만 이전(완전 보상하지 않음).
3. **끼니 배분**: 남은 끼니에 §3.2 비율로 배분하고 간식은 `snack_share`로 분리.
4. **영양소 구성**: 끼니 열량을 다량영양소 비율(§3.1)로 나누고, 그 비율에 맞는 음식 1~5개를 참조표(§3.4)에서 골라 `serving_qty`를 정한 뒤 **음식 합이 끼니 열량과 ±10% 안에서 맞도록** 마지막 음식 양을 조정한다. 미량영양소는 음식에서 따라온다.
5. **진짜 소모** = 기초대사량 × PAL × exp(N(0, 0.10)) (+ 운동 세션 열량).
6. **진짜 체중**: 전날 체중 + (섭취 − 소모) / 7,700 × 0.5(§3.5). 
7. **관측**: A축으로 그날·그 끼니를 기록할지 정하고, C축으로 열량·간식을 깎고, D축으로 착용·부분 착용·체중 측정 여부와 수신 지연을 정한다.
8. 출력 테이블에 쓰고, 진실은 `persona_truth_daily`에 쓴다.

## 3. 수치 매개변수와 출처

### 3.1 섭취 — 기대 섭취량과 영양소 구성

| 항목 | 값 | 출처 |
|---|---|---|
| **진짜** 하루 열량의 기준 | 에너지 균형: 기초대사량 × PAL(§3.5). "유지" 페르소나는 이 값의 1.0배를 먹어 체중이 변하지 않는다 | 설계 §5.1의 기초대사량 식, PAL 범주 |
| 국민건강영양조사 기대값 | 회귀 모형 `exp(expected_log)`(성·연령·키·체중)을 `persona_manifest.expected_kcal`에 대조용으로 남긴다. 조사 섭취량은 보고값이라 에너지 균형보다 낮으므로 진실 기준으로 쓰지 않는다 | `data/knhanes_reference_model.json`, `KNHANES_2022_2024_v1` |

C축 혼합 비율은 **관측된 섭취/기초대사량 비율 분포**가 운영 집계(3끼 기록일, 10/25/50/75/90백분위 **0.55 / 0.90 / 1.21 / 1.50 / 1.78**)에 맞도록 정한다. 진실 기준이 에너지 균형(기초대사량 × PAL ≈ 1.4~1.55 BMR)이므로 기록 계수 0.7~0.8이 관측 비율 1.2 안팎을 만든다. 이 분포는 중앙값이 과소보고 컷오프 1.35 아래라는 사실 자체가 중요한 발견이므로(자문 질문 Q2의 배경), 보정 목표로 고정한다.

## 10. 테스트에서의 사용 규칙

1. **정답 대조.** 모든 규칙 테스트는 `persona_truth_daily`·`persona_manifest`를 정답으로 쓴다. 예: C2 사용자의 3끼 기록일 중 섭취/기초대사량 비율 < 1.35인 날의 비율이 C0 사용자보다 유의하게 높아야 한다. 수치 기준은 "방향이 맞는가"로만 두고 민감도·특이도 수치는 보고하지 않는다.
2. **스냅숏 재현.** 재계산 테스트는 `available_from ≤ 계산일`로 그 날 시점의 웨어러블 행만 보이게 해서 계산한다.
3. **표기.** 페르소나로 낸 모든 표·그림에 "합성(persona v1)" 표기. 보고서에 넣을 때는 §0.3의 한계를 함께 적는다.
4. **실제 데이터 재검증.** 페르소나로 통과한 테스트 목록을 `docs/persona_test_matrix.md`에 남기고, 실제 기록이 쌓이면 같은 목록을 실제 데이터로 다시 돌린다. 임계값은 그때 확정한다(설계 §5.4 "측정 전 기준 확정"은 그대로 적용).
5. **갱신.** 운영 분포가 바뀌면(예: 웨어러블 보유율 상승) 매개변수 파일의 보정 목표를 새 조회 날짜와 함께 갱신하고 버전을 올린다. 이전 버전 산출물은 지운다.
6. **적재 금지.** 페르소나 데이터는 개별 작업이므로 공유 DB(loop-dev, release)에 넣지 않는다. 식이분석 코드를 페르소나로 돌릴 때는 로컬 PostgreSQL에 `load_local.sql`로 올리거나 CSV를 직접 읽는다.
