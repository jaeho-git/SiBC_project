# 페르소나 데이터 생성 로직 — 어떤 사용자의 어떤 데이터가 어떤 자료에서 나오는가 (2026-11-02)

독자: 페르소나 데이터로 식이분석 시스템을 구현할 팀 내 개발자. 이 문서는 식이(`meal`·`meal_food`)와 웨어러블(`baseline_lifelog_daily`) 페르소나 데이터를 **하나의 생성 로직**으로 묶어, 세 가지 질문에 답한다.

1. **출처.** 생성된 값 하나하나가 어떤 자료(식약처 영양성분 참조, 국민건강영양조사, 운영 DB 집계, 공식, 가정)에서 나왔는가.
2. **재생성.** 새 사용자가 필요할 때 그 자리에서 어떻게 만들고, 기존 데이터 옆에 어떻게 붙이는가.
3. **사용.** 만들어진 데이터가 식이분석 구현의 어느 단계 입력이 되고, 어떤 정답표로 결과를 대조하는가.

식이 처리 순서는 [dietary_record_processing_logic_20261102.md](dietary_record_processing_logic_20261102.md), 웨어러블 생성 순서는 [wearable_persona_generation_logic_20261102.md](wearable_persona_generation_logic_20261102.md), 수치의 근거는 [persona_data_spec_20261027.md](persona_data_spec_20261027.md)에 있다. 이 문서는 그 셋을 **입력 자료 → 사용자 1명 → 출력 열**의 흐름으로 다시 묶은 것이며, 수치가 어긋나면 명세와 매개변수 파일을 따른다.

생성기 버전: `persona.2026.10.27-v1` (2026-11-02 옵션 추가: `--user-seq-start`, `--append`, 검사기 `--integrity-only`).

## 0. 핵심 요약

### 목적

페르소나 데이터는 난수로 "그럴싸하게" 만든 것이 아니라, **고정된 입력 자료 4종**과 **사용자 정의 1행**에서 결정적으로 계산된 것이다. 그래서 어떤 행이든 출처를 거슬러 올라갈 수 있고, 같은 입력이면 같은 결과가 나오며, 유형표에 1행을 더 쓰면 새 사용자가 즉시 만들어진다. 이 세 성질이 있어야 개발자가 페르소나 데이터를 **시스템 구현의 입력**으로 믿고 쓸 수 있다.

### 핵심 결론

> 사용자 1명은 **유형표 1행**(성·연령대·BMI 구간·축 5개·가이드라인·수신 프로필·재정의)에서 시작한다. 생성기는 이 1행과 고정 입력 자료 4종 — 식약처 참조에서 뽑은 **음식 풀 260종**(1인분 영양 21열), **국민건강영양조사 회귀 모형**(대조용 기대 열량), **운영 DB 집계값**으로 맞춘 **매개변수 파일**, **공식·문헌값**(기초대사량·PAL·7,700 kcal/kg) — 만으로 210일을 하루씩 돈다. 하루마다 진짜 섭취·소모·체중을 먼저 정하고(진실 층), 그 위에 기록 여부·과소보고·음식 분해·착용·기기 편향·도착일을 씌워(관측 층) `meal`·`meal_food`·`baseline_lifelog_daily` 행을 쓰고, 진실은 `persona_truth_daily`·`persona_manifest`에 남긴다. **음식 영양은 항상 식약처 참조 1인분 값 × 인분 수**이고, 끼니 합계는 음식 합이며, 기기 소모는 진짜 소모 × 0.87 × 사용자 편향이다. 새 사용자는 유형표 파일에 1행을 쓰고 `--user-seq-start`로 번호를 이어 붙여 0.2초에 만든다. 산출물은 로컬 파일로만 두고 공유 DB에는 적재하지 않는다.

### 결정 사항

| 결정 항목 | 결론 | 근거 강도 | 핵심 근거 |
|---|---|---|---|
| 음식 영양의 원천 | 식약처 전국통합식품영양성분정보 → 1인분 환산표 → 음식 풀 260종. **LLM 추정값을 쓰지 않음** | 강함 | 실제 `meal_food`도 참조 1인분 × 인분 수로 전환 예정(food_reference §3.2·§7.3) |

| 격리 | 로컬 파일 전용, `99999999-` 접두 UUID, 로컬 스키마 `sibc_persona` | 강함 | 2026-10-27 결정 |

### 이 문서가 다른 문서와 다른 점

| 문서 | 묻는 질문 | 이 문서와의 관계 |
|---|---|---|
| 페르소나 명세 | 왜 이 수치인가, 어떤 유형이 있는가 | 수치의 **근거 원본**. 이 문서는 수치를 반복하지 않고 출처 종류만 적는다 |
| 식이 기록 처리 로직 | 끼니 입력 1건이 어떤 순서로 처리되는가 | 그 1~4단계를 생성기가 **관측 층**으로 구현한다(§3.3) |
| 웨어러블 생성 로직 | 소모·체중이 어떤 순서로 baseline 행이 되는가 | 그 7단계를 §3.2·§3.4에 요약하고 출처 열을 붙인다 |
| **이 문서** | 어떤 값이 어떤 자료에서 나왔고, 새 사용자를 어떻게 만들며, 구현에 어떻게 쓰는가 | 입력 자료 → 사용자 1명 → 출력 열의 **계보(lineage)** |

## 1. 전체 구조

```text
[고정 입력 자료 — git 추적, 생성마다 동일]
  ① 음식 풀            data/persona_food_pool_v1.csv        식약처 참조 → 1인분 환산 → 260종
  ② 기대 열량 모형     data/knhanes_reference_model.json    국민건강영양조사 2022~2024 회귀
  ③ 매개변수           data/persona_params_v1.toml          운영 DB 집계(2026-10-27) + 문헌 + 가정
  ④ 공식               생성기 코드                          Mifflin-St Jeor, PAL, 7,700 kcal/kg

[사용자 정의 — 1행 = 1유형, n명]
  ⑤ 유형표             data/persona_types_v1.csv (또는 추가용 파일)
                       성·연령대·BMI 구간·축 A/B/C/W/S·가이드라인·수신 프로필·n·재정의 JSON

            │  python tools/build_persona_data.py --types ⑤ [--user-seq-start N --append]
            ▼
[생성기  tools/build_persona_data.py — 표준 라이브러리만, DB 접속 없음]
  사용자마다:  프로필 → 210일 하루 루프(진실 층 → 관측 층 → 정답 행) → user_master·manifest

            ▼
[출력 — 로컬 CSV(UTF-8 BOM) + load_local.sql(로컬 PostgreSQL 전용) + run_info.json]
  실제 포맷:  user_master, meal, meal_food, baseline_lifelog_daily
  정답표:     persona_manifest(사용자 1행), persona_truth_daily(사용자×날짜 1행)
```

생성기는 ①~⑤ 외의 어떤 것도 읽지 않는다. 환경 변수, `.env`, DB 드라이버를 쓰지 않으므로 어느 PC에서 돌려도 같은 입력이면 같은 출력이 나온다(테스트 `test_generation_is_deterministic`).

## 2. 입력 자료와 출처

### 2.1 ① 음식 풀 — 식약처 참조의 1인분 영양값

| 항목 | 내용 |
|---|---|
| 원자료 | 식약처 **전국통합식품영양성분정보** 표준데이터(Open API `tn_pubr_public_nutri_info_api`, 346,592행, 기준일 2026-09-29). `00_Data/`(git 제외) |
| 1차 가공 | `tools/build_food_reference.py` → `01_Results/food_nutrient_reference_per_serving.csv`(git 제외). 100 g/100 ml 기준값을 **1인분 환산**(음식: 식품중량 = 1인분, 가공식품: 식약처 1회 섭취참고량 규칙표 `data/processed_food_serving_rule.csv`). 등급 FULL/CORE/PARTIAL, 품질 플래그 부여. 상세 food_reference.md §7 |
| 2차 가공 | `tools/build_persona_food_pool.py` → **`data/persona_food_pool_v1.csv`(git 추적)**. FULL 등급·품질 플래그 없음·열량 15~1,200 kcal(간식 슬롯 ≤ 400)·탄단지·나트륨 보유 행만 후보로 두고, 슬롯별 상한(주식 30·면 25·국 40·반찬 90·김치 15·빵 25·음료 20·유제품 15)으로 결정적 추출(시드 20261027). 이름 중복 제거 |
| 풀의 열 | `food_code`, `food_name`, `food_name_norm`, `data_type`(음식/가공식품), `major_name`(식약처 대분류), `slot`, `serving_qty`·`serving_unit`(1인분 g 또는 ml), 영양소 21열 **1인분 기준** |
| 생성기에서의 역할 | `meal_food`의 `food_name`·`food_name_norm`·영양소 21열·`estimated_amount_g`의 **유일한 원천**. 생성기는 이 파일 밖의 음식을 만들지 않는다 |
| 한계 | 비타민 E는 식약처 참조에 없어 항상 NULL. 트랜스지방·미량영양소도 참조 공란이면 NULL(0이 아님). 실제 앱의 `meal_food_master`(21,172건)는 쓰지 않으므로 마스터 연결률은 음식명 변형 30 %로만 시험 |

음식 풀의 어떤 행도 개인 데이터가 아니다. 공개 참조의 집계값이므로 git에 둔다.

### 2.2 ② 기대 열량 모형 — 국민건강영양조사

| 항목 | 내용 |
|---|---|
| 원자료 | 질병관리청 국민건강영양조사 기본DB 2022·2023·2024(SAS). `00_Data/knhanes/`(git 제외, 재식별·제3자 제공 금지) |
| 가공 | `tools/build_knhanes_reference.py`. 만 19세 이상·영양조사 참여·500~5,000 kcal 16,106명. 가중 최소제곱 `log(섭취량) ~ 1 + 여성 + 연령 + 연령²/100 + 신장 + 체중 + 주말` → **`data/knhanes_reference_model.json`(git 추적)**. 참조 버전 `KNHANES_2022_2024_v1` |
| 생성기에서의 역할 | **`persona_manifest.expected_kcal`에 대조용으로만 기록.** 진실 섭취의 기준으로는 쓰지 않는다(아래 ④). 식이분석의 맥락 층(집단 백분위)이 같은 모형을 쓰므로, 페르소나 사용자에 맥락 층을 적용했을 때 결과가 설명 가능한지 확인하는 데 쓴다 |
| 함께 있는 자료 | `data/knhanes_reference_dist.csv`(성·연령대·BMI 구간별 영양소 백분위). 생성기는 직접 읽지 않으며, 영양소 편향 페르소나(B7·B8·B10)의 목표 구간을 정할 때 명세가 참조했다 |

### 2.3 ③ 매개변수 파일 — 운영 DB 집계 + 문헌 + 가정

`data/persona_params_v1.toml`의 모든 수치에는 주석으로 출처 종류가 붙어 있다.

| 출처 표기 | 뜻 | 예 |
|---|---|---|
| `measured` (운영 집계) | release DB `invites_loop`를 **집계 쿼리로만** 읽은 값. 조회 2026-10-27, 식이 창 2026-09-01~10-26. 개인 행은 읽지 않음 | 하루 열량 변동 계수 0.25, 끼니 시각 중앙값 8/13/18시, 야식 비율 11 %, 총소모 10/50/90백분위 1,249/1,455/1,850, 심박 `n_records` 분포, 수신 지연 중앙값 4.4일·90백분위 23.5일, 체중 측정 잡음 0.4 kg, 웨어러블 보유율·착용률·부분 착용 40 % |
| `measured` (문헌·외부) | 공개 문헌·기준 | PAL 범주(FAO/WHO/UNU 2004), 7,700 kcal/kg, KDRIs 필요추정량, 과소보고 하한 1.35 |
| `assumption` | 관측 목표를 맞추기 위해 둔 가정. 측정값이 아님 | 진짜 결식률 10/5/3 %, 간식 발생 50 %, 전 끼니 기록일 65 %, 늦은 시각 기록 22 %, 기록 지연 70/25/5 %, 기기 편향 ±8 %, 체중 감쇠 0.3, 운동 250 kcal·45분·18:30 종료 |
| `[[calibration]]` 32개 | 생성 결과가 맞춰야 하는 운영 집계 목표와 허용 오차 | 핵심 기록자 비율, 끼니 부재율, 섭취/기초대사량 비율 분포, 총소모 분포, 도착 지연 분포 등 |

가정값은 **관측 결과가 운영 집계와 맞도록** 역산된 것이므로 그 자체는 실제 행동의 측정이 아니다. 예를 들어 "진짜 결식률 10 %"는 측정이 아니고, 관측 끼니 부재율 13 %를 결식과 미기록으로 나누기 위한 배분이다. 이 구분이 중요한 이유는 §6.4에 있다.

### 2.4 ④ 공식 — 코드에 고정된 계산

| 공식 | 쓰이는 곳 | 출처 |
|---|---|---|
| 기초대사량 Mifflin-St Jeor: 남 10W + 6.25H − 5A + 5, 여 10W + 6.25H − 5A − 161 | `manifest.bmr_kcal`, 진짜 소모, `active_kcal_burned`, 섭취 진실 기준 | 설계 §5.1 과소보고 탐지와 같은 식 |
| 진짜 소모 = 기초대사량 × PAL × exp(N(0, σ)) (+ 운동 250) | `true_expenditure_kcal` | PAL 고령 1.38 / 일반 1.55 / 활동형 1.80 |
| 진짜 섭취 기준 = 기초대사량 × PAL | `true_intake_kcal`의 기준값 | 에너지 균형. "유지" 유형이 체중을 유지하도록 |
| 체중 변화 = (섭취 − 소모) / 7,700 × 0.3, 하루 ±0.15 kg 상한 | `true_weight_kg` | 정적 환산에 적응 감쇠를 둔 단순화 |
| 기기 총소모 = 진짜 소모 × 0.87 × 사용자 편향 × 부분 착용 계수 | `total_kcal_burned` | 운영 중앙값이 추정보다 13 % 낮음 |
| 활동 소모 = max(0, 총소모 − 기초대사량 × 1.1) | `active_kcal_burned` | 운영 중앙값 125에 맞춤 |
| 걸음 = exp(ln 5,785 + (PAL − 1.5) × 2 + N(0, 0.55)) | `step_count` | 운영 10/50/90백분위 |
| 도착 지연 ~ 로그정규(중앙값, 90백분위에 맞춤), 30일 절단 | `burn_available_from` | 운영 수신 지연 분포 |

### 2.5 ⑤ 유형표 — 사용자 정의 1행

`data/persona_types_v1.csv`의 열. **새 사용자는 이 형식의 1행이다**(§5).

## 5. 새 사용자를 그때그때 만드는 절차

### 5.1 언제 쓰는가

- 구현 중 특정 분기(예: "7일 창 식이 4일·웨어러블 3일·동시 2일")를 밟는 사용자가 필요할 때.
- 앱 파트 시연용으로 특정 프로필(68세 여성, BMI 25, 웨어러블·체중계 보유)의 사용자가 필요할 때.
- 운영에서 새로 관찰된 패턴을 재현해 회귀 테스트에 넣을 때.

기존 710명 세트를 다시 만들지 않고, **추가분만** 만든다.

### 5.2 절차

1. 유형표 파일을 새로 만든다. 헤더는 `data/persona_types_v1.csv`와 같고, 1행에 1유형을 쓴다. `n`은 보통 1. 수용 기준으로 쓸 사용자는 `deterministic: true`로 둔다.

```csv
code,name,sex,age_band,bmi_lo,bmi_hi,axis_a,axis_b,axis_c,axis_w,axis_s,guideline,arrival,n,overrides
N01,신규: 68세 여성·과체중·착실·웨어러블·체중계,F,65-74,24.0,26.0,A1,B1,C1,W2,S2,,ios,1,"{""profile"": {""height_cm"": 156, ""weight_kg"": 62}}"
```

2. 기존 세트의 마지막 일련번호를 확인한다(`run_info.json`의 `user_seq_end`, 710명 세트는 710).

3. 생성한다. 출력 폴더는 기존 세트와 **다른 폴더**로 둔다.

```bash
cd dietary_analysis_model
python tools/build_persona_data.py --types path/to/types_new.csv \
  --user-seq-start 711 --append --out 01_Results/persona_add_20261102 --seed 7
```

4. 정합성만 검사한다(소수 사용자는 보정 32개 지표를 맞출 수 없으므로 `--integrity-only`).

```bash
python tools/check_persona_calibration.py --dir 01_Results/persona_add_20261102 --integrity-only
```

5. 로컬 PostgreSQL에서 쓰려면 추가분의 `load_local.sql`을 실행한다. `--append`로 만든 SQL은 DDL이 없어 기존 `sibc_persona` 테이블에 행만 덧붙인다. **공유 DB에는 실행하지 않는다.**

6. 유형표 파일과 명령(시드·시작 번호)을 함께 보관한다. 같은 입력이면 같은 사용자가 다시 나온다.

### 5.3 옵션 요약

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--types` | `data/persona_types_v1.csv` | 유형표. 추가 생성은 별도 파일 |
| `--out` | `01_Results/persona` | 출력 폴더. 추가 생성은 별도 폴더 |
| `--seed` | 20261027 | 난수 시드. 사용자 내용은 `시드:코드:번호`로 결정 |
| `--user-seq-start` | 1 | 첫 사용자의 일련번호. 기존 세트 마지막 + 1 |
| `--append` | 꺼짐 | `load_local.sql`에 DDL(drop/create) 없이 `\copy`만 |
| `--codes` | 전체 | 유형표 중 일부 코드만 |
| `--scale`, `--max-per-type` | 1.0, 없음 | 인원 배수·상한. 소규모 시험용 |
| `--params`, `--pool`, `--model` | `data/` 기본 파일 | 입력 자료 교체(버전 변경 시) |

`run_info.json`에 버전, `run_id`, 시드, 인원, 일련번호 범위, `append` 여부, 사용한 유형표·매개변수·음식 풀 경로, 테이블별 행 수가 기록된다.

### 5.4 주의

- `user_id`는 시드와 무관하게 **일련번호**다. 시작 번호를 안 바꾸면 기존 세트와 충돌한다.
- 매개변수·음식 풀 파일을 바꾸면 기존 세트와 같은 규칙이 아니다. 바꿀 때는 `[meta].version`을 올리고 전체를 다시 만든다.
- 소수 추가 생성분을 710명 세트의 집계(보정 지표·창 상태 분포)에 섞어 보고하지 않는다. 추가분은 분기 재현·시연용이다.
- 가이드라인 지정 사용자는 `guideline` 열에 코드를 쓴다. 생성기는 이 값을 manifest에 옮길 뿐 섭취를 바꾸지 않는다(가이드라인은 판정 쪽 입력).

## 6. 시스템 구현에서의 사용

### 6.1 어느 단계의 입력인가

| 식이분석 단계(설계 §8) | 입력 테이블 | 정답표 대조 |
|---|---|---|
| 1~4단계 음식 식별·환산·끼니 확정 | 생성기가 **이미 수행**. `meal`·`meal_food`가 결과 | 구현한 규칙으로 `meal_food` → `meal` 합계를 다시 계산해 일치 확인 |
| 5단계 하루 누적·완전성 | `meal`, `meal_food` | `persona_truth_daily.recorded_main_meals`, `skipped_meals`(A10의 SKIPPED 행과 대조), `recorded_day` |
| 6단계 행동 층 결과 값 | `meal` + `user_master`(기초대사량) | `manifest.bmr_kcal`, `true_intake_factor`; 과소보고 탐지는 `underreport_factor`로 양성/음성 구분 |
| 7~8단계 하루 확정·습관 층 기준일 행 | `meal` 전체 | `true_intake_kcal`의 창 평균 vs 관측 창 평균(과소보고 계수만큼 낮아야 함) |
| 9단계 웨어러블 결합 | `baseline_lifelog_daily` (+ 일별 행에서 파생한 창) | `wear`, `partial`(n_records < 480과 일치), `true_expenditure_kcal`, `burn_available_from`으로 시점 스냅숏 |
| 체중 추세·방향 | `baseline_lifelog_daily.weight_kg`, `user_master.weight` | `true_weight_kg` |
| 맥락 층 집단 백분위 | `user_master` + 창 평균 | `manifest.expected_kcal`과 같은 모형이므로 결과가 설명 가능해야 함 |

### 6.2 시점 스냅숏

웨어러블 행은 측정일보다 늦게 도착한다. "월요일 계산 시점"을 재현하려면 `persona_truth_daily.burn_available_from ≤ 계산일`인 날의 소모 행만 보이게 걸러 계산하고, 목요일 시점으로 다시 계산해 **같은 기준일 행이 섭취만 → 완전으로 바뀌는지** 확인한다. 식이 행은 실시간 원천이므로 `created_at ≤ 계산 시각`으로 같은 처리를 할 수 있다.

### 6.3 로컬 실행

식이분석 코드를 페르소나로 돌리려면 로컬 PostgreSQL에 `load_local.sql`을 실행하고 코드가 읽는 스키마를 `sibc_persona`로 바꾼다(현재 `sibc` 고정, 매개변수화가 전제). CSV를 직접 읽어도 된다(utf-8-sig, 빈 칸 = NULL).

### 6.4 해석의 한계

- 페르소나로 나온 모든 수치는 **"합성(persona v1)"**으로 표기한다. 임계값 확정, 거짓 알람률, 행동 변화 효과는 페르소나로 측정하지 않는다.
- §2.3의 `assumption` 값은 관측 목표를 맞추기 위한 배분이다. 예를 들어 과소보고 탐지가 C2 사용자를 잘 잡는다는 결과는 "규칙이 가정대로 동작한다"는 뜻이고, 실제 과소보고자를 잡는다는 뜻은 아니다.
- 핵심 기록자의 웨어러블 보유(실제 17 %, 생성 약 36 %)와 완전 주 비율(실제 20 %, 생성 약 40 %)은 분기 커버리지를 위해 **의도적으로 과대** 표현되어 있다. 창 상태 분포를 보고할 때 함께 적는다.

## 7. 수용 기준 — 출처 추적이 되는가

구현 전에 생성 데이터 자체가 이 문서를 만족하는지 확인하는 항목. 2026-11-02 추가 생성분(N01, 1명)에서 모두 확인했다.

| # | 확인 | 방법 | 기대 |
|---|---|---|---|
| 1 | 음식 영양 = 참조 1인분 × 인분 수 | `meal_food`에서 DONE 행을 뽑아 `food_name_norm`(변형 접미 제거)으로 음식 풀 행을 찾고 `energy_kcal`을 재계산 | 전 행 일치(소수 3자리). UNKNOWN 행은 전부 NULL |
| 2 | 끼니 합 = 음식 합 | `meal` 영양소 21열 vs 같은 `meal_id`의 `meal_food` 합 | 전 행 일치. 정합성 검사 항목 |
| 3 | 기초대사량 재현 | `manifest`의 성·나이·키·시작 체중으로 Mifflin-St Jeor 계산 | `bmr_kcal`과 일치 |
| 4 | 기기 소모 재현 | `total_kcal_burned` ÷ (`true_expenditure_kcal` × 0.87 × `device_bias`) | 완전 착용일 1.0, 부분 착용일 0.8~0.95 |
| 5 | 미착용일 행 없음, 부분 착용 = `n_records < 480` | `truth.wear/partial` vs baseline 행 존재·`heartrate_bpm.n_records` | 정합성 검사 항목 |
| 6 | 날짜 귀속 | `meal.ymd` = `eaten_at` KST 날짜 | 전 행. 자정 이후 야식은 다음 날 |
| 7 | 결정성 | 같은 유형표·시드·시작 번호로 두 번 생성 | 모든 CSV의 해시 동일 |
| 8 | 추가 생성 격리 | `--user-seq-start 711 --append` | `user_id` 접미 000000000711부터, SQL에 drop/create 없음 |
| 9 | 입력 자료 외 참조 없음 | 생성기 소스에 psycopg2·os.environ·.env 없음 | 테스트 `test_outputs_exist_and_no_db_code` |

오프라인 테스트 19건(`tests/test_persona_generator.py`)이 1·2·5·6·7·8·9를 자동으로 확인한다.
