# 웨어러블 페르소나 데이터 생성 로직 — 소모·활동·심박·체중이 baseline 행이 되는 순서 (2026-11-02)

독자: 페르소나 데이터로 식이분석의 웨어러블 결합(설계 §8 6단계)을 구현·검증하는 개발자. 페르소나 생성기 `tools/build_persona_data.py`가 웨어러블 쪽 행을 **어떤 순서와 규칙으로** 만드는지, 그것이 실제 웨어러블 데이터 경로의 어느 지점에 해당하는지를 적는다.
근거는 데이터 확인 결과 [data_check_20261026.md](data_check_20261026.md) §1(웨어러블 baseline DB), 완전성 규칙 초안 [completeness_rules_draft_20261026.md](completeness_rules_draft_20261026.md) §2, 페르소나 명세 [persona_data_spec_20261027.md](persona_data_spec_20261027.md) §1.3·§3.5~§3.7, 식이 기록 처리 로직 [dietary_record_processing_logic_20261102.md](dietary_record_processing_logic_20261102.md) §7.4다.

생성기 버전: `persona.2026.10.27-v1`. 매개변수는 `data/persona_params_v1.toml`의 `[expenditure]`, `[weight]`, `[wearable]`, `[axis_w.*]`, `[axis_s.*]`에 있다.

## 0. 핵심 요약

### 목적

식이 기록은 사용자가 끼니마다 입력하지만, 웨어러블은 기기가 측정하고 플랫폼이 늦게 모은다. 그래서 웨어러블 페르소나는 "무엇을 먹었나"가 아니라 **"몸이 얼마나 썼는가(진실)"와 "기기가 그중 얼마를 언제 서버에 보냈는가(관측)"**를 나눠 만든다. 이 문서는 그 두 층의 생성 순서와, 식이분석이 읽는 `baseline_lifelog_daily` 포맷으로 내려오는 규칙을 적는다.

### 핵심 결론

> 웨어러블 페르소나는 하루마다 **진짜 소모(기초대사량 × PAL × 일별 변동 + 운동 세션)**와 **진짜 체중(에너지 수지에 따라 느리게 변함)**을 먼저 정한 뒤, 그 위에 **착용 여부 → 부분 착용 → 기기 편향·과소 추정 → 서버 도착일**의 관측 과정을 씌워 `baseline_lifelog_daily` 행(심박·총소모·활동소모·걸음·운동·체중·BMI)을 만든다. 미착용일은 행을 만들지 않고, 부분 착용일은 심박 `n_records`를 480 미만으로 두어 완전성 규칙이 그 날 소모를 쓰지 않게 한다. 도착일(`burn_available_from`)은 정답표에만 두어 "월요일 시점"과 "목요일 시점"의 재계산을 재현한다. 원천(discovery) 수준·시간대 수준·창(window) 수준은 만들지 않으며, 일별 행에서 창을 파생하는 것이 식이분석의 책임이다.

### 결정 사항

| 결정 항목 | 결론 | 근거 강도 | 핵심 근거 |
|---|---|---|---|
| 생성 수준 | 원천·시간대 수준이 아니라 **일별 baseline 행** | 강함 | 식이분석이 읽는 입력이 `baseline_lifelog_daily / _window`(설계 §3.1). 원천 13개 테이블은 식이분석 범위 밖 |
| 미착용 표현 | 행 없음(0이 아님) | 강함 | 실제 baseline도 측정이 있는 날만 행이 생김(data_check §1.1) |
| 부분 착용 표현 | 심박 `n_records < 480` | 강함 | 착용 시간 열이 없어 심박 측정 수를 대리 지표로 씀(완전성 규칙 §2) |
| 기기 과소 추정 | 총소모 = 진짜 소모 × 0.87 × 사용자 편향(±8 %) | 중간 | 운영 총소모 중앙값 1,455 kcal이 기초대사량 × PAL 추정보다 약 13 % 낮음. §5.1 소모 타당성 평가 대상 |
| 수신 지연 | 로그정규(중앙값 4.4일, 90백분위 23.5일, 최대 30일), 정답표에만 기록 | 강함 | 운영 calories 원천 `ins_dt − measured_dt` 분포(data_check §1.3) |
| 체중 | 체중계 보유자만, 측정일만, 진짜 체중 + N(0, 0.4) | 중간 | 운영 체중 보유 203명, 8주 측정일 중앙값 2일, 사용자 내 표준편차 0.54 kg |
| 하루 경계 | KST 00~24시, `measure_date` 1행 | 강함 | 실제 baseline과 동일(data_check §1.1) |

## 1. 실제 웨어러블 데이터 경로와 페르소나가 들어가는 지점

```text
[기기] 워치·밴드·체중계 측정 (분 단위 심박, 세션 단위 활동, 일 합계 열량, 측정 시 체중)
   │  iOS: 백그라운드 전송 / Android: 앱 실행 시 전송  → 측정일보다 늦게 도착(중앙값 4.4일)
   ▼
[discovery 원천] disc_lifelog_user_* 13개 테이블. measured_dt(측정)·ins_dt(수신) 분리
   │  baseline 파이프라인(ichms-sibc-ontology-be/reliable_model/baseline_pipeline), 매일 새벽
   ▼
[baseline] hourly(사용자×지표×날짜×시) → outlier_point → daily(사용자×지표×날짜) → window(기준일×창 7/14/30/60/180)
   │  최근 35일 DELETE+INSERT 재계산, measured_dt 기준 KST 날짜 귀속, 미측정일 행 없음
   ▼
[식이분석] baseline daily/window 읽기 → 웨어러블 유효일·동시 유효일·에너지 지수·체중 추세 → 창 상태
```

페르소나 생성기는 **[baseline] daily 수준**의 행을 직접 만든다. 기기·원천·hourly·window는 만들지 않는다. 식이분석 코드가 window 행을 직접 읽도록 구현되면 일별 행에서 같은 규칙(창 길이별 평균, `n_days_covered`)으로 파생한다(명세 §11 #4).

## 2. 생성 순서 (사용자 1명, 하루 1일 기준)

```text
프로필 (성·연령·키·체중 → 기초대사량, 활동 수준 PAL, 장치 축 W/S, 수신 지연 프로필, 기기 편향)
  │
  ▼ 진실 층 (매일)
  ① 진짜 소모 = 기초대사량 × PAL × exp(N(0, 0.08))  (+ 운동 세션이 있는 날 250 kcal)
  ② 진짜 체중 = 전날 체중 + (진짜 섭취 − 진짜 소모) / 7,700 × 0.3   (하루 ±0.15 kg 상한)
  │
  ▼ 관측 층 (매일)
  ③ 착용 여부   보유자(W1/W2)만. Bernoulli(착용률) → 미착용이면 그날 기기 행 없음
  ④ 부분 착용   착용일 중 Bernoulli(부분 착용률) → 심박 n_records 73~479, 소모 기록 계수 0.8~0.95
  ⑤ 기기 관측   총소모 = 진짜 소모 × 0.87 × 사용자 편향 × 부분 계수 → 심박·활동소모·걸음·운동 행
  ⑥ 도착일      burn_available_from = measure_date + 지연(프로필별 로그정규, 최대 30일)
  ⑦ 체중계      보유자(S1/S2/S3)만. Bernoulli(측정 확률) → weight_kg·bmi 행, 도착 0~1일
  │
  ▼ 출력
  baseline_lifelog_daily 행(지표별 1행) + persona_truth_daily 1행(진실·착용·도착일)
```

같은 날의 식이 기록(식이 기록 처리 로직 1~4단계)과는 독립적으로 생성되며, 둘을 잇는 것은 `user_id`와 KST 날짜뿐이다. 설계가 "같은 날 00~24시"로 섭취와 소모를 맞추기로 했기 때문이다(설계 §3.6).

## 3. 단계별 규칙

### 3.1 프로필에서 정해지는 것

| 항목 | 규칙 | 출처 |
|---|---|---|
| 기초대사량 | Mifflin-St Jeor: 남 10W + 6.25H − 5A + 5, 여 10W + 6.25H − 5A − 161 | 설계 §5.1 과소보고 탐지와 같은 식 |
| PAL | 65세 이상 1.38, 그 외 1.55, 활동형(B9) 1.80. 결정적 페르소나가 아니면 ± N(0, 0.05) | FAO/WHO/UNU 2004 범주, 운영 소모 중앙값에 맞춤 |
| 운동 요일 | 활동형 주 4회, 그 외 주 1회. 요일은 사용자별 고정(난수). 결정적 페르소나는 활동형일 때만 | 가정 |
| 장치 축 W | W0 없음 / W1 착용률 0.55·부분 0.40 / W2 착용률 0.90·부분 0.30. 유형표에서 혼합 비율로 뽑을 수 있음 | 운영 집계(명세 §3.6) |
| 장치 축 S | S0 없음 / S1 일 측정 확률 0.03 / S2 0.07 / S3 0.90 | 운영 8주 측정일 중앙값 2일 |
| 수신 지연 프로필 | 유형표 지정이 없으면 iOS형 15 % / Android형 85 % | 설계 §3.1의 전송 방식 차이 |
| 기기 편향 | 사용자별 고정 U(−0.08, +0.08) | 가정. 결정적 페르소나는 0 |

### 3.2 진실 층

| 단계 | 규칙 | 비고 |
|---|---|---|
| 진짜 소모 | `bmr × pal × exp(N(0, σ))`, σ는 변동 계수 0.08에 해당. 운동일은 + 250 kcal | 결정적 페르소나는 σ = 0 |
| 운동 세션 종료 시각 | 18:30 KST 고정 → `persona_truth_daily.exercise_end_at` | 식이의 "운동 후 2시간" 플래그 정답 |
| 진짜 체중 | `W(t) = W(t−1) + clamp((섭취 − 소모) / 7,700 × 0.3, ±0.15)`. 시작 체중은 프로필의 BMI에서 역산 | E11은 체중 계획(§3.6)으로 대체 |

진짜 소모는 식이 쪽 진짜 섭취의 기준값이기도 하다(명세 §3.1: "유지" 페르소나의 진짜 섭취 = 진짜 소모 × 1.0). 그래서 에너지 지수의 정답은 페르소나 유형의 `intake_factor`에서 바로 나온다(예: B2 1.25배 → 지수 +25 %).

### 3.3 관측 층 — 착용

```python
def wears(user, date) -> (wear, partial):
    if not user.wear_owner:                      return False, False
    if wear_from_week and week_rel(date) < wear_from_week:  return False, False     # E17: 마지막 4주만 보유
    if wear_weekdays_cycle:                      return (weekday in cycle[week % len]), False   # E02
    if deterministic or wear_all:                return True, False
    if rand() >= wear_rate:                      return False, False               # 미착용일: 행 없음
    return True, rand() < partial_rate                                             # 부분 착용일
```

### 3.4 관측 층 — 기기 행 (착용일에만)

| `metric_code` | `value` | `n_records` | 부가 열 | 규칙 |
|---|---|---|---|---|
| `heartrate_bpm` | 안정 심박 U(60, 80) + N(2, 3), 소수 1자리 | 완전 600~1,300 / **부분 73~479** | `value_min = value − 12`, `value_max = value + 55`, `value_stddev = 11.5` | `n_records`가 착용 시간 대리 지표. 완전성 규칙 §2의 480 경계를 정확히 가른다 |
| `total_kcal_burned` | round(진짜 소모 × 0.87 × 기기 편향 × 부분 계수) | 1 | — | 부분 계수 U(0.8, 0.95)는 부분 착용일만 |
| `active_kcal_burned` | max(0, total − 기초대사량 × 1.1) | 1 | — | 운영 중앙값 125 kcal에 맞춤 |
| `step_count` | exp(ln 5,785 + (PAL − 1.5) × 2 + N(0, 0.55)) × 부분 계수 | 1 | — | 운영 10/50/90백분위 1,246 / 5,785 / 14,162 |
| `activity_kcal` | 250 | 1 | — | 운동일만 |
| `activity_duration_min` | 45 | 1 | — | 운동일만 |

모든 행에 `run_id`(생성기 실행 식별자), `computed_at`(가상의 오늘 03:00 KST)을 넣는다. `value_p25/p75`, `n_excluded`, `ref_*`, `outlier_flag`, `deviation_score`는 비워 둔다(식이분석이 읽지 않음).

### 3.5 관측 층 — 도착일

```python
def arrival_delay_days(user, date):
    if arrival_schedule_last_week and week_rel(date) == -1:        # E13: 요일별 지정 도착일
        return (schedule[weekday] - date).days
    if deterministic: return 0
    mu, sigma = lognormal_from(median, p90)                         # 프로필: android 4.4/23.5, ios 1.0/7.0, extreme 20/29
    return min(max_days(30), round(lognormvariate(mu, sigma)))
burn_available_from = measure_date + arrival_delay_days
```

도착일은 `baseline_lifelog_daily`에 없다(실제 테이블에도 없음). `persona_truth_daily.burn_available_from`에만 두고, 테스트는 `available_from ≤ 계산일`인 행만 보이게 걸러 **특정 날짜 시점의 스냅숏**을 만든다. 심박·걸음·운동 행은 같은 날 같은 기기에서 오므로 소모와 같은 도착일을 공유한다.

### 3.6 관측 층 — 체중계

| 항목 | 규칙 |
|---|---|
| 측정 여부 | 보유자만, 하루 Bernoulli(측정 확률). E11은 "마지막 30일에 n일, 그 전 150일에 m일"을 균등 간격으로 지정 |
| `weight_kg` | round(진짜 체중 + N(0, 0.4), 1). 결정적 페르소나는 잡음 0 |
| `bmi` | round(관측 체중 / 키², 1) |
| 도착일 | 측정일 + U{0, 1}일 → `persona_truth_daily.weight_available_from` |
| `user_master.weight` | **생성 시작일의 진짜 체중을 반올림한 값으로 고정.** 체중계가 있어도 갱신하지 않음 | 

마지막 줄이 중요하다. 실제 `user_master`에 체중 갱신 이력이 없으므로(data_check §3), 방향 층의 BMI는 가입 시 체중으로 계산되고 체중 추세만 체중계 행에서 나온다. 체중이 변하는 페르소나(P02·P17·P15)에서 두 값이 벌어지는 것이 의도된 상태다.

## 6. 만들지 않는 것과 확장 방법

| 항목 | 현재 | 필요해지면 |
|---|---|---|
| 원천 수준(`disc_lifelog_user_*`, measured_dt/ins_dt) | 생성 안 함 | baseline 파이프라인 자체를 시험할 때만 필요. 일별 행과 도착일에서 역으로 분 단위 심박·세션을 펼치는 생성기를 추가 |
| `baseline_lifelog_hourly` | 생성 안 함 | 시간대별 소모(설계 §5.2 A형 "시간대별 소모량")를 다룰 때. 일 합계를 24시간 프로필(수면 저·활동 고)로 배분 |
| `baseline_lifelog_window` | 생성 안 함, 파생 | 6단계 코드가 window를 직접 읽으면 일별 행에서 창 길이별 평균·`n_days_covered`를 같은 규칙으로 계산해 적재 |
| 수면·혈압·SpO2·체성분·악력 | 생성 안 함 | 식이분석이 읽지 않음. 야식 플래그를 "취침 전 N시간"으로 바꾸면 수면 시작 시각(`sleep_*`)이 필요해짐 |
| 기기 종류·운영체제 메타데이터 | 도착 지연 프로필(iOS/Android)로만 | 기기별 소모 추정 편향 층화(설계 §5.1)를 하려면 `persona_manifest`에 기기 종류 열 추가 |
| 심박 안정값의 개인 고정 | 하루마다 U(60, 80) | 개인 안정 심박 추세를 쓰게 되면 사용자별 고정값 + 일별 잡음으로 변경 |
