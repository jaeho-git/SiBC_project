# 인바이츠루프 V5 AI Agent 컴피티션: 3+1 구현 전략

작성일: 2026-10-28  
근거: 컴피티션 공지, V5 설명, 3대 KPI, 6대 지침, 최신 세계관, SiBC Handbook 및 검증 프레임워크.  
**표기:** [확정] 제공 자료에 명시 / [제안] 개발 전략 / [미확인] 추가 자료 필요.

## PART 1. 결론

[제안] **3+1을 각각 시연하는 대신, W→M1→M3→W에서 하나의 실제 작동 루프로 연결**하는 것이 핵심이다. 온톨로지가 데이터의 의미와 근거를 연결하고, JITAI가 개입/대기/재확인을 판단하고, HITL이 사람의 승인·수정·거절을 관리하며, +1 자기개선이 개입·반응·결과를 평가해 개선 후보를 검증한다.

[확정] 공식 평가는 세계관·3대 KPI·6대 지침·3+1 **34점**, 기술 완성도·통합성 **33점**, 설치·운영·유지보수 **33점**이다. 3+1만으로 고득점이 보장되지는 않는다. [확정] 최신 세계관은 V5의 3대 KPI 측정체계와 V6의 3+1 본격 도입을 구분한다. [제안] 이번에는 **V6를 지향하는 3+1의 검증 가능한 최소 작동 버전**을 구현하되 공식 버전명과 완전한 임상 검증을 혼동하지 않는다.

## PART 2. 3+1의 구현 정의

| 요소 | 최소 실제 동작 | 검증할 증거 | 피해야 할 오류 |
|---|---|---|---|
| 온톨로지 | 자기보고·측정·추정·의사 판단·계획·수행을 출처·시점·관계로 연결 | evidence refs, event time, plan version | 자기보고를 확진으로 취급 |
| JITAI | 현재 유효 계획·동의·데이터 품질에 따라 개입/침묵/재확인/검토 요청 | decision, reason, policy version | 장기 IRS+ 위험을 급성 안전 판단에 전용 |
| Human-in-the-Loop | 의료진·사용자의 승인·수정·보류·거절을 실제 상태에 반영 | reviewer role, 승인 시각, 감사 기록 | 승인 없이 계획 확정 |
| +1 재귀적 자기개선 | 개입·반응·결과 평가→개선 후보→오프라인 시험→인간 승인 | 후보별 비교, 기각 사유, rollback | 검증 없이 임상 정책 자동 변경 |

**중요:** 기억을 많이 쌓는 것만으로 자기개선이 아니다. **판단/개입 정책의 변경 후보를 평가하고, 승인된 개선만 적용**해야 한다. 또한 3+1은 엄격한 직렬 처리만 뜻하지 않는다. 근거가 부족하면 즉시 ABSTAIN할 수 있다.

## PART 3. 추천 데모: 한 사람의 여정

1. **W:** 합성 사용자가 생활 목표·제약을 말한다. 자기보고로 기록하고 실제 측정과 구분한다.
2. **온톨로지:** 과거 맥락, 데이터 출처·시점, IRS+ 참고정보, 유효 계획을 연결한다. “왜?” 질문에 당시 사용한 근거만 제시한다.
3. **JITAI:** 신선한 데이터와 동의가 있으면 허용된 생활 개입을 제안한다. 오래된 값·결측·동의 부재에서는 RECHECK/ABSTAIN/HUMAN_REVIEW로 분기한다.
4. **M1:** 의료진이 Patient Summary를 검토해 계획을 승인·수정·보류한다.
5. **M3:** 사용자가 실행상 어려움을 말하면 변경안을 제시하지만 승인 전에는 기존 계획을 유지한다.
6. **다시 W:** 최신 승인 계획만 안내하고 이전 계획·근거는 보존한다.
7. **+1:** 반응·수행 근거·오류를 이용해 정책 후보 A/B를 같은 합성 평가셋에서 비교한다. 기준 미달 후보는 기각한다.
8. **운영:** 다른 테스트 환경에서 재설치해 동일 시연과 자동시험을 재현한다.

**M2:** 세계관에는 포함되지만 공지의 명시적 연속 과제는 W→M1→M3다. 시간 부족 시 M2는 축소 시연으로 관리한다. 급성 우선순위를 IRS+ 장기 위험만으로 결정하지 않는다.

## PART 6. 데이터분석가인 내가 담당할 부분

**추천 역할: 3+1 Data Quality & Decision Validation Lead.** 질문은 “데이터가 존재하는가?”가 아니라 **“이 사용자·시점·목적의 AI 판단에 이 데이터를 써도 되는가?”**다.

| 우선 | 담당 과제 | 직접 산출물 | 3+1 연결 |
|---|---|---|---|
| P0 | 데이터 품질·활용 적합성 | 품질 규칙, USE/RECHECK/ABSTAIN 판정 | 온톨로지·JITAI |
| P0 | 판단 근거 일치성 | AI 응답·개입과 원자료·시점 대조 시험 | 온톨로지·HITL |
| P0 | W/M1/M3 정합성 | 환자·계획·권한·버전 통합 테스트셋 | 전체 |
| P1 | 개입-반응-결과 계약 | intervention/exposure/response/outcome 구조 | +1 |
| P1 | JITAI 보류 규칙 | 결측·시간 지연·불확실성 분기표 | JITAI |
| P1 | HITL 검토 트리거 | 근거 부족·충돌·권한 문제 검토 요청 | HITL |
| P1 | 자기개선 검증 | 고정 평가셋·baseline·안전 게이트 | +1 |
| P1 | KPI 측정 프로토콜 | 분모·분자·측정시점·출처 | 34점 평가 |
| P2 | 기관·기기 품질 드리프트 | 환경별 데이터 품질 모니터링 | 운영·+1 |

**실제 협업 방식:** 사용자는 데이터 계약·규칙·평가셋·검증보고서를 정의하고 개발자 또는 코딩 Agent가 이를 API·DB·UI에 연결한다. 사용자는 검증 결과와 배포 게이트를 책임진다. 단순 데이터 제공자가 아니라 **AI 판단의 품질과 재현성 책임자**가 된다.

**SiBC 자산 사용 제한:** Reliability의 공식 scoring scope는 **exercise only**다. sleep/stress/diet를 공식 신뢰도 점수로 확장하지 않는다. 건강검진 예측은 **BLOCKED_BY_DATA**이며 검증된 성능이나 개인 예측이 없다. 데이터 누출(time/user/environment)을 방지하고, 근거 부족 시 ABSTAIN/검토 필요로 처리한다.

## PART 8. 필수 검증 시나리오

1. 정상 데이터에서 허용된 생활 개입과 정확한 근거가 출력되는가?
2. 결측·오래된 데이터에서 ABSTAIN/RECHECK하는가?
3. 자기보고/측정/추정/의사 확정을 구분하는가?
4. 다른 사용자·기관 기록이 혼입되지 않는가?
5. 미래 정보가 과거 판단에 유입되지 않는가?
6. 의료진 승인 전 계획을 변경하지 않는가?
7. 구버전 화면에서 최신 계획을 덮어쓰지 않는가?
8. 동일 요청 재전송이 중복 실행을 만들지 않는가?
9. 취소 요청을 실제 취소 완료로 오인하지 않는가?
10. 신호 끊김을 정상·안전한 침묵으로 오인하지 않는가?
11. 개선 후보가 안전 기준에 미달하면 기각되는가?
12. 새 환경에서 같은 설치·데모·시험이 재현되는가?

시험 기준값은 실제 데이터와 임상/운영 정책을 확인한 뒤 **사전에 확정**해야 한다. 합성 테스트 통과를 실증 성과로 표시하지 않는다.

## PART 9. 더 정확한 전략 수립을 위해 필요한 정보

### A. 최우선: 개발 방향을 결정하는 6가지

| 순위 | 요청할 자료/질문 | 필요한 이유 | 자료가 없을 때의 임시 조치 |
|---|---|---|---|
| 1 | **V5 및 H1의 실제 소스코드·저장소·실행 방법**: HTML 단일 파일인지, 서버/DB/API가 있는지, 기존 자동시험은 무엇인지 | 이미 구현된 3+1과 누락된 부분을 구분하고 재작업을 막기 위해 | 문서 기반 설계까지만 확정, 구현 수준은 미확인으로 표시 |
| 2 | **팀 구성·역할·개발 가능 인력·AI Agent 도구**: 본인이 어느 팀인지, 백엔드/프론트/DevOps 담당이 있는지 | 2주 안에 실현 가능한 범위와 책임을 결정하기 위해 | 데이터 계약·평가셋 작업을 독립 과제로 시작 |
| 3 | **실제 연결 가능한 데이터 목록과 스키마**: IRS+·웨어러블·SiBC·iCHMS·EMR 각각의 현재 상태, 가명화된 샘플 여부 | 온톨로지·JITAI의 실제 입력을 결정하기 위해 | 합성 데이터로 검증, 실데이터 적용은 별도 보류 |
| 4 | **3+1 평가의 공식 기대 수준**: 구현 필수 기능, V6 명칭 사용 여부, 시연/소스/설치 중 무엇을 평가하는지 | 과도한 개발과 잘못된 우선순위를 방지하기 위해 | ‘최소 작동 루프+검증 증거’ 전략 채택 |
| 5 | **임상·규제·의료진 승인 범위**: IRS+ 표시 허용범위, JITAI 개입 허용행위, M1 승인 담당자 | 의료적 판단·규제 경계를 안전하게 정하기 위해 | 생활지원/모의 승인만 시연하고 민감 기능은 검토 필요로 표시 |
| 6 | **현장 구축 대상 환경**: 클라우드/온프레미스, 병원별 설정, OS, 인증·DB·네트워크 제약 | 운영·재구현 33점 대응을 위해 | 재현 가능한 표준 테스트 환경을 먼저 구축 |

### B. 다음 단계에서 필요한 6가지

7. **기존 SiBC 규칙·평가모델·품질 기준:** 어떤 모듈이 실제 운영 중이고 무엇이 연구/모의인지, 입력·출력 계약과 공식 scope는 무엇인지.
8. **온톨로지/공통 원장 스키마:** event type, 관계, 계획 상태, 권한, 시간 및 provenance 구조.
9. **JITAI 정책 명세:** 개입 목적, 허용 개입, 재확인 간격, 침묵 상태, 위험 신호의 담당 주체.
10. **HITL 운영 정책:** 승인·보류·수정 권한, 임상적 책임, 승인 이후 적용 시각, 취소·철회 처리.
11. **KPI 기준 데이터:** 오류·사용성·참여·운영 사건, 청구·원가 자료의 유무와 출처; 실제/시뮬레이션 구분.
12. **평가단 발표 형식:** 시연 시간, 설치 재현 요구, 제출물 형식, 질의응답과 데모 환경.

### C. 가능하면 확보할 검증용 자료

- 기존 H1 시험 코드·로그·실패 케이스와 수정 내역. 보고된 통과 건수는 직접 재현 전까지 **자료상 보고값**으로 취급.
- 사용자·의료진이 실제로 수행하는 대표 과업 3~5개 및 UX 피드백(실제 수용성 측정에 필요).
- 기관·기기·기간별 데이터 품질 통계. 개인정보는 가명화·집계된 수준으로 제공.
- IRS+ 모델 문서: intended use, 입력 범위, 유전체 입력 여부, 위험 출력의 의미, 검증·규제 상태.
- 기존 3대 KPI 산식과 목표값이 있다면 해당 문서. 목표가 없으면 임의로 성공 기준을 정하지 않음.

## PART 10. 자료를 받았을 때 수행할 분석 절차

1. **Inventory:** 코드·화면·API·데이터·시험·배포 자산을 목록화하고 `구현됨/모의/부분/미구현/미확인`으로 분류.
2. **Traceability:** 3대 KPI·6대 지침·3+1의 각 요구사항을 코드 모듈, 데이터 계약, 테스트, 데모 장면에 연결.
3. **Gap & Risk:** 점수 영향, 개발 난이도, 임상·규제 위험, 데이터 가용성에 따라 우선순위 산정.
4. **Scenario Freeze:** 평가에 사용할 대표 W→M1→M3→W 여정 하나를 고정하고 성공/실패 경로를 확정.
5. **Agent Work Packages:** 담당자별로 입력·출력·허용범위·완료 조건·자동시험을 갖춘 개발 티켓으로 분해.
6. **Validation:** 정해진 기준으로 정상·결측·시간·권한·중복·복구·근거 일치성을 검증.
7. **Release Gate:** 테스트·문서·설치 재현·임상 검토 상태가 충족될 때만 발표 후보로 승인.

## PART 11. 최종 권고와 제한사항

### 결론

**가장 중요한 것은 3+1의 ‘존재’가 아니라 ‘검증 가능한 작동’이다.** 온톨로지가 근거를 연결하고, JITAI가 적절히 개입 또는 보류하며, HITL이 실제로 계획을 통제하고, 자기개선이 검증·승인된 변경으로 이어져야 한다. 여기에 설치 재현성과 3대 KPI 계측을 결합해야 공식 100점의 세 평가영역을 균형 있게 준비할 수 있다.

### 변경/권고

- **첫 48시간:** 소스·팀·데이터·평가 요구를 확인하고 대표 데모 한 개를 확정.
- **데이터분석가의 P0:** Data Usability Gate + 근거 일치성 테스트 + W/M1/M3 정합성 검증.
- **개발팀의 P0:** 공통 원장/상태 기계, JITAI/HITL 연결, 종단간 자동시험, 재설치 자동화.
- **+1은 P1:** 자동 자율 변경이 아니라 **후보 생성→평가→인간 승인→버전 관리**로 안전하게 구현.

### 검증

최종 발표 전에는 **정상 동작뿐 아니라 실패 시 안전하게 멈추는 동작**, 다른 환자·시점·권한 오류 방지, 정책 변경의 승인 기록, 동일 환경 재현을 반드시 보여준다. 실제/모의/미검증 기능을 발표 화면과 문서에서 구분한다.

### 제한사항

현재 문서는 제공된 설명과 프로젝트 지침을 바탕으로 한 **전략 설계**다. 실제 V5/H1 코드·DB·API·운영자료를 직접 점검한 결과가 아니므로 구현 현황과 일정의 실현 가능성은 **검토 필요**다. 건강검진 예측은 `BLOCKED_BY_DATA`이고 검증된 개인 예측 성능은 없다. SiBC Reliability 공식 범위는 `exercise only`다. 의료 진단·치료 판단을 대신하지 않으며, Secret·원시 식별자·원시 건강정보를 문서나 시연 로그에 출력하지 않는다.
