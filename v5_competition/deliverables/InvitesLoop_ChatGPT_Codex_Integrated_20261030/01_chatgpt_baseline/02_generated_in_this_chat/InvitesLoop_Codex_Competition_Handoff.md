# 인바이츠루프 AI Agent 개발 컴피티션 — Codex 인수인계

작성일: 2026-10-29 | 상태: **PLANNING / 코드·H1 패키지 미검증**

> **Codex의 최상위 목표:** V5 프로토타입을 기반으로 W→M1→M3→W가 실제 상태를 공유하는 소프트웨어를 구현하고, **3+1(JITAI, 온톨로지, Human-in-the-Loop, 재귀적 자기개선)**이 하나의 근거 기반 시나리오에서 작동하도록 한다. 실제 임상 모델을 2주 안에 완성하려 하지 않는다. 합성 페르소나 데이터로 기능·안전·재현성을 검증하며, 모의 성능과 임상적 유효성을 절대 혼동하지 않는다.

- 경쟁: **2026-10-28~11-10**, 발표 **11-11**. SH·iCHMS·SiBC·대전팀, A/B/C 3팀, AI Agent 조직·기술 스택 자율.
- 공식 과제: **V5 프로토타입 고도화**, W→M1→M3 연속 경험, IRS+·SiBC·iCHMS 연계, 세계관 반영, 설치·운영·유지보수 용이성.
- 평가: 세계관·3대 KPI·6대 지침·3+1 **34점** / 기술 완성도·통합성 **33점** / 현장 구축·운영·재구현 **33점**.
- 공식 명칭은 V5 경쟁. 최신 세계관 자료에서 **3+1 본격 도입은 V6**로 구분. 이번에 3+1의 실제 작동하는 핵심 경로를 보여주는 것은 **전략적 권고**이며 공식적으로 V6 전체 완성을 요구한다고 단정하지 않는다.
- 최우선 산출물: (1) 실행 가능한 통합 데모 (2) 근거 기반 합성 페르소나 DB (3) 데이터 품질·사용 적합성 게이트 (4) 승인·근거·상태 원장 (5) 3+1 자동 테스트 (6) 설치·운영 문서와 KPI 측정 계약.

## PART 2. 제품 세계관과 UX — 구현 시 보존

**Designing Your Life, Beyond Time**은 제품 정의다. `iSignature`(과거의 나)·`iPresent`(현재의 나)·`iFuture`(미래의 선택/조건)를 하나의 시간축에서 연결한다. 의료의 단위는 episode가 아니라 **journey**이며 `W→M1→M2→M3→W`는 경험·개입·반응·결과가 누적되는 나선형 루프다. 검증되지 않은 미래 질병 수치를 예언하지 않는다.

- **L3 인바이츠루프 OS**: 공통 기억·계획·권한·근거·명령 실행. 앱·키오스크·닥터웹·경영 화면 및 향후 Agent/Physical AI는 접점.
- **IRS+**: 유전체 기술 융합 건강위험 추론. 실제 개인 유전정보 입력 여부와 기술 기반을 구분한다.
- **Signature/Identity**: 개인 맥락·설명 선호. **SiBC**: 무엇을/언제/어떻게 개입하거나 침묵·재확인할지 결정; **JITAI는 SiBC 내부 기능**.
- **iCHMS**: 여정·계획 버전·승인·업무·수행·운영/재무 백본. 예상 EBITDA, 관찰 실적, 검증된 귀속효과를 분리.
- **C2 LLM**은 의도 해석·후보·설명을 생성할 뿐, 사실·의사 승인·실제 수행을 임의 확정하지 않는다. **L3의 검증된 명령 API**만 권한 있는 쓰기를 수행한다.
- UX: **Everything Behind, Almost Nothing in Front**, **Same Data, Different Expression**, 누구도 소외되지 않는 UI. W=조용한 AI 건강비서, M1=Patient Summary, M2=Dynamic Priority Queue, M3=Shared Health View. 결론→이유→상세자료. 사실은 같고 표현만 다르게.
- 공지의 **필수 연결 경로는 W→M1→M3**. M2는 전체 세계관에 포함되지만 이번 2주 내 구현 범위는 팀과 협의하여 결정.

### 6대 지침
1. IRS+·유전체 정체성을 W/M1/M2/M3에 반영하되 표시 범위는 법률 검토 후 결정.
2. 의사가 확정한 질환명은 다음 W에서 **의사 판단 전달**로 표시하고 앱 자체 진단과 구분.
3. 첫 W의 위험·우선순위 이해→의료진 확인→신뢰 형성 흐름을 설계·측정.
4. 일반 지침 인용과 개인 판정을 구분하고, 일반 LLM과 달리 개인의 여정·의료진 판단을 온톨로지로 연결.
5. 규제 회색지대는 무조건 삭제/출시하지 말고 법률·병원 협의 및 실증/샌드박스 검토 대상으로 관리.
6. 유전체 활용 시나리오와 신뢰·이행률·의료진 불일치율 측정 계약 설계.

## PART 3. 3+1 작동의 최소 완료 기준

| 요소 | 최소 작동 기능 | 통과 증거 |
|---|---|---|
| **온톨로지** | 자기보고·측정·모델추정·의사확정·계획·개입·반응·결과를 출처·시점·관계로 연결 | 판단에 사용된 근거·버전·출처를 역추적 |
| **JITAI** | 유효 계획·현재 상황·품질·권한에 따라 개입/침묵/보류/재확인 | 입력 변경 시 결정 변화, 근거 부족 시 ABSTAIN |
| **HITL** | 의료진/사용자 승인·수정·거절·철회·보류 | 승인 전후 계획 상태 분리, 권한과 버전 기록 |
| **재귀적 자기개선** | 모의 개입 결과 평가→개선 후보→고정 시험셋 비교→인간 승인 후 제한 적용 | 이전/후 성능 비교, 회귀 시 차단·롤백 |

**중요:** 대화 기억이나 페르소나 축적만으로 '재귀적 자기개선'이라고 주장하지 않는다. 임상 정책·진단·안전 임계치는 자동 변경하지 않는다. 검증되지 않은 개선안은 `REVIEW_REQUIRED`로 남긴다.

### 대표 종단간 시연
1. **W:** 합성 사용자 생활 제약·질문 입력 → 현재 유효 계획과 허용된 관찰 조회.
2. **Data Gate:** 결측·오래된 값·출처 충돌 시 `ABSTAIN/REVIEW_REQUIRED`; 임의 예시값 대체 금지.
3. **JITAI:** 비임상 범위의 일정/표현 조정 제안 또는 침묵; 임상 변경 필요 시 검토 요청.
4. **M1:** 의료진이 근거 확인 후 계획 승인/수정/보류. 초안을 현재 계획으로 표시 금지.
5. **M3:** 환자·의료진이 동일 사실과 계획을 역할별 표현으로 공유. 변경 요청과 승인 분리.
6. **다시 W:** 승인된 최신 계획만 적용하고 이전 결정·근거 조회.
7. **+1:** 합성 반응·실행 결과로 개입 후보 평가; 검증/승인 전 자동 적용 금지.

## PART 4. 데이터분석가 담당 — 근거 기반 페르소나 DB

**권장 직무:** `Evidence-Based Persona Data & AI Decision Validation Lead`.

실제 데이터 사용 적합성·품질·예측모델·근거·표준화의 전 과정을 2주 내 끝내는 것은 비현실적이다. 이번에는 **실제 데이터를 대체한다고 속이지 않는 합성 페르소나 DB와 공통 검증 계약**을 만들어 개발자에게 연결한다.

### 최소 엔터티 계약(제안; 저장소 확인 후 확정)

| 테이블/엔터티 | 최소 필드/개념 |
|---|---|
| `persona` | 합성 ID, 시나리오, seed, 생성 버전, 선호, `synthetic=true` |
| `observation` | 값/단위, 데이터 유형, 측정/기록/수신 시각, 출처, 신호 품질 |
| `evidence` | 출처/규칙 참조, 유효기간, 판단 목적, 검토 상태 |
| `quality_assessment` | 결측·유효성·일관성·최신성·중복·단위, 사유와 규칙 버전 |
| `usability_decision` | 목적별 `ALLOW/LIMITED/REVIEW_REQUIRED/ABSTAIN/DENY`, 근거 |
| `clinical_assertion` | 자기보고 vs 의사 확정, 승인자 역할, 근거·상태 |
| `plan_version` | draft/approved/scheduled/active/held/cancelled, 승인·적용 시각 |
| `intervention` | 판단 시점 입력·규칙·개입/침묵·요청 ID·상태 |
| `response` / `outcome` | 전달/열람/수용/거절/실제 수행/결과 미확인 구분 |
| `improvement_proposal` | 기존 정책·후보·오프라인 평가·승인·배포/롤백 |
| `audit_event` | actor role, action, target, version, timestamp, 결과(민감값 제외) |

**값의 의미:** `actual`, `measured`, `reported`, `pred`, `risk`, `score`, `probability`는 서로 다르며 혼용 금지. **품질점수는 정답 확률이 아니다.** 합성 예시는 `DEMO_ONLY`, 검증되지 않은 의학적 임계치는 `UNVALIDATED`로 표시한다.

### 페르소나 5종
- **P01 정상:** 데이터 적합·승인 계획 → 정상 루프.
- **P02 품질 불량:** 결측/오래된 웨어러블 → ABSTAIN·재확인.
- **P03 제약 변화:** 생활 일정 변경 → JITAI 제안·권한 확인.
- **P04 승인 충돌:** 오래된 계획·승인 전/후 → HITL 버전 차단.
- **P05 반복 반응:** 개입·거절·수행 이력 → 개선안 비교·승인·롤백.

추가 경계조건: 다른 환자 접근, 동의 철회, 중복 명령, 미래 시점 데이터, 단위 충돌, 측정 중단, 취소 요청/실제 취소 확인 분리.

### 품질과 사용 가능성은 별개
1. **Quality QA:** 완전성·유효성·일관성·최신성·출처/중복/단위 확인.
2. **Purpose-specific Gate:** 목적·동의·권한·임상 승인·모델 검증 상태·시점에 따라 사용 여부 판정.
3. 품질이 높아도 해당 목적에 부적합하면 **ABSTAIN**. 결측을 정상으로 간주하지 않는다.

## PART 5. SiBC 공식 제한사항 — Codex 강제 준수

- 기본 문맥: `01_SiBC_DataScience_Handbook(1).md`, `02_SiBC_Data_Quality_Framework(1).md`, `09_SiBC_Model_Validation_Framework(1).md`.
- **Reliability의 공식 scoring scope는 `exercise only`.** sleep/stress/diet는 공식 신뢰도 점수로 확장하지 않는다.
- **건강검진 예측모델은 `BLOCKED_BY_DATA`.** 검증된 모델 성능이나 개인 예측값은 없다. 합성 결과를 `pred` 또는 임상 성능으로 포장하지 않는다.
- **time/user/environment leakage 방지:** 판단 시점 이후의 값 사용 금지, 동일 사용자 데이터의 학습/평가 누출 방지, 데모·시험·운영 데이터 및 Secret 분리.
- 근거 부족 시 **`ABSTAIN` 또는 `REVIEW_REQUIRED`**, 허위 근거·고정 검사값·임의 정상 판정 금지.
- 임상 진단·치료 판단 대체 금지. Secret·원시 식별자·원시 건강정보를 문서·화면 로그·커밋에 노출하지 않는다.
- 개선/재학습은 별도 검증과 승인 후 적용. 모의 데이터에서 통과한 테스트는 임상 성능을 입증하지 않는다.

## PART 6. 3대 KPI 측정 설계 (V5의 핵심)

| KPI | 데모에서 실제로 검증 가능한 항목 | 실증 없이는 주장하지 않을 항목 |
|---|---|---|
| **① 구동 안정성·임상 유효성** | API 성공/실패율, 명령 중복 차단, 최신 계획 정합성, 근거 추적률, 테스트 통과율, 데이터 품질 거부율 | 실제 임상적 유효성·안전성 확보 |
| **② 사용자·의료진 수용성** | 시연 과업 완료시간, 단계 수, 화면 이해도 조사 설계, 사용성 시험 계측 | 실제 환자 유지율·장기 수용성 |
| **③ 재무개선·지속가능성** | 비용·수가·참여 조건을 입력받는 **가정 기반 시뮬레이션**, 산식 재현성, 입력·출력 추적 | 실제 청구 성과, 검증된 순 ΔEBITDA, 귀속효과 |

운영 로그에서 **`simulation / observed / verified_attributable`** 구분을 강제한다. KPI별 정의서에는 분자·분모·기간·데이터 소스·제외 조건·측정 시점·검증 책임자를 명시한다. 신뢰→참여→재무의 연결은 **세계관의 인과 가설**이며, 검증되지 않은 인과 효과를 사실로 단정하지 않는다.

## PART 7. Codex 실행 순서 — 저장소에서 실제로 할 작업

### 7.1 착수 전 읽기·탐색 (코드 수정 전 필수)

1. 현재 디렉터리, Git 상태, 브랜치, 주요 파일·패키지·테스트·설치 스크립트 조사.
2. 기존 V5/H1 파일과 앱 실행방법, API·DB·인증·원장·시뮬레이터 유무 파악.
3. `README`, `AGENTS.md`, 아키텍처·데이터 계약·테스트 설정을 읽고 충돌하는 지침을 보고.
4. **시작 상태 스냅샷**: 실행 성공/실패, 현재 테스트 통과 수, 주요 버그, 누락 기능을 증거와 함께 기록.
5. **Gap Matrix** 작성: 요구사항 / 현재 구현 / 결함 / 우선순위 / 담당 / 수용 테스트 / 상태.
6. 실제 코드가 없으면 임의로 기존 구현이 있다고 가정하지 말고, **최소 실행 앱 신규 생성 여부를 사용자에게 확인**.

### 7.2 개발 원칙

- 기존 파일·원본 프로토타입은 보존. 변경 전 브랜치/커밋으로 복구 지점 확보.
- 작은 단위로 구현→테스트→커밋. Agent 간 파일 충돌 방지를 위해 소유 범위와 API 계약을 먼저 확정.
- **데이터/권한/명령/상태 엔진을 먼저**, 그 위에 화면과 AI Agent를 연결한다.
- LLM을 쓰더라도 **결정·승인·실행의 최종 진실은 검증된 원장/규칙/권한**에 둔다.
- 임상 안전성·개인정보·규제 미확정 부분은 모의 기능과 승인 필요 기능을 분리.
- 데모용 고정 대사만 재생하는 구현은 금지. 입력을 바꾸면 출력·근거·상태가 실제로 달라져야 한다.
